Context system: the map, layers and rooms

Every agent tool reads the same short rules file first. The owner calls it the map.

One file, many tools

The map is one Markdown file in a git repo. A Nix home-manager config links it into the place each tool expects:

ToolReads at start
Claude Code~/.claude/CLAUDE.md
Codex~/.codex/AGENTS.md
OpenCode~/.config/opencode/AGENTS.md
Gemini CLI~/.gemini/GEMINI.md
backpass (rule proposer)~/.agents/AGENTS.md

All five are links to the same file. Change the map once, and every tool sees the change in its next session.

The map holds house rules, a "who does what" list, and a routing table. The routing table says: for this kind of task, go to this folder and read these files first.

Five layers

Context comes in layers, from broad to narrow. An agent loads only the layers its task needs.

Rooms

A room is a folder for one kind of work. Its CONTEXT.md names the input, the task, the output and a check. Examples in this setup:

  • Writing room. A voice file with tone rules. It grows from the owner's feedback. Drafts are review pages.
  • Software factory room. Eight numbered stages from intent to "learn". See Planning.
  • Study room. One note per topic, mapped to things already built.

Rooms follow the stage-contract idea from Jake Van Clief's ICM (see Influences). That idea has three parts: ordered stages, a contract per stage, and taste rules in their own files.

A design rule: the core is pure

The owner thinks of the map and rooms as the core of a hexagon. Tools are adapters that plug in through the links. Nothing outside writes into the core. A tool may propose an edit. The owner applies it.

Tests

Plain shell tests check the structure, with no model calls:

  • tests/run.sh: map shape, rooms, routes, links. 58 pass, 0 fail (2026-10-30).
  • tests/e2e-probe.sh: asks each agent for a "canary" word from the map. This proves the agent really loaded it. designed, not proven on 2026-10-30. It costs tokens, so this draft did not run it. This session did load the map.
