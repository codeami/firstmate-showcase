The idea

Visitor

Why not just use a chat with a good model?

First Mate

A model is only as good as the harness around it.

Visitor

Harness?

First Mate

Everything around the model: the rules it reads, the tools it may use, the checks on its work, and the notes it keeps.

What a plain chat does not do

Visitor

So what do you do that a chat does not?

First Mate

I hand coding work to coding agents. Each gets one task, its own copy of the code, and a written brief. A scout finds facts. A ship changes code.

First Mate

I track your tasks. A sprint board has six phases. A task leaves a phase only when that phase's exit check is true.

First Mate

I explain myself. Every report, plan or draft for you becomes a page you can mark up. Your notes go back to the agent that wrote it.

First Mate

I extend myself, but you approve it. Skills load only when a task needs them. A tool called backpass reads old sessions and proposes edits to my rules. It never writes them.

First Mate

runs daily The backpass job runs daily. It proposes rule edits, and you approve them.

First Mate

I learn and teach. Each session ends with notes: goals, decisions, and where the agent went its own way. Reports are written in short, plain sentences, and a checker flags long ones.

First Mate

General office work is planned too. The plan is staff bots for the board, the inbox and drafts. designed, not run

How it is set up

Visitor

How is this built?

First Mate

Four layers on top of Claude Code, which does the building.

First Mate

1. The orchestrator. That is me. I am the one point of contact. I write the briefs and start the workers.

First Mate

2. Isolated copies. Each worker gets its own git worktree. That is a separate copy of the code, so a worker cannot break your main copy.

First Mate

3. Review boards. Pages where you read the work and leave notes. You do not review in a terminal.

First Mate

4. Instruction files. One short rules file, called the map, is read first by every agent. The map is the product.

The big one

Visitor

Fine. But how do I know the work is right?

First Mate

Nothing lands until it has been checked three times.

  1. The worker checks its own work. It backs each claim with a command or a file read.
  2. The gates check it again. Hooks block unsafe actions. Tests check the rules. the full pre-push gate was not run for this site
  3. You give the word. Only you can merge, publish, send or spend.

It works on me too. The manual once said scouts run with permission checks on. A check found all 10 running workers had them off. The manual was fixed. Read the case.

Visitor

That is a lot of checking.

First Mate

Yes. It is the point. Until a check passes, a claim is called "in trial", never a feature.

First Mate

One honest note: workers skip permission checks by default. A model-reviewed mode is being trialled. The page Cast and authority says more.

Memory

Visitor

Do you remember things between sessions?

First Mate

Not in my head. In files. Four kinds: the rules, this chat, a store of reports and notes, and an index that says where things are.

First Mate

The index is rebuilt at the start of each session. It exists because an agent once searched the web for work that was already on disk.

First Mate

The same rules file is linked into five tools: Claude Code, Codex, OpenCode, Gemini CLI and backpass. Change it once and all five see it next session.

First Mate

Two parts do not work yet. One saves facts before a chat is squeezed into a summary. The other files facts into a learnings file. not working designed, not proven

The vendor idea

Visitor

So how should I think about all this?

First Mate

The owner puts it this way: managing a complex AI agent system is sort of like managing a contract with different vendors.

First Mate

You scope the work. You write down who may do what. You ask for status. You accept work only on evidence. You decide what happens when it goes wrong.
