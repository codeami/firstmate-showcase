How it works

One person, many coding agents, one set of rules

The owner talks to one supervisor agent. The supervisor runs worker agents. Every agent reads the same short rules file. The owner approves every change that matters.

It runs today

This is a working system, not a design. It runs daily on the owner's machine.

One of its workers built this site. About 110 scout reports are on disk. On one day, four workers ran in parallel. Three each delivered a reviewed pull request on a public repo: this site, reels4mphotos and swarm-referee. The fourth delivered a private package.

The supervisor and most worker mechanics are upstream Firstmate, MIT licence, by Kun Chen and contributors. The owner built the rules file, the hooks, the work index and the review flow.

1. The supervisor

The owner asks for work in plain words. The supervisor writes a brief for each task. Then it starts one worker for that task.

Each worker writes short status lines to its own file. A small shell script watches those files. It uses no model tokens. It wakes the supervisor only when a worker needs something.

Each worker is a normal agent session in a visible terminal window. It is not a tool's built-in sub-agent. A built-in sub-agent is hard to see and hard to steer, and its work can die with its parent. Upstream records one such loss.

2. The workers

A worker is one agent on one task. There are two kinds.

Scout

Finds facts. It writes a report. Nothing is pushed.

Ship

Changes code. It opens a pull request. The owner says when it merges.

Each worker gets its own git worktree. That is a separate, disposable copy of the code. A worker cannot break the owner's main copy.

3. The life of one task

  1. Brief. The intent, the rules and where to write.
  2. Worktree. A clean copy of the code.
  3. Report or pull request. With evidence: the commands run and the files read.
  4. Completion gate. A worker may not close a task while a question for the owner is open.

This site went through these steps. Its brief said: write only in the site folder, remove personal details, credit upstream, and never push.

designed, not proven The full ship path with the pre-push gate was not run for this site.

4. One rules file for every tool

Every agent tool reads the same short rules file first. The owner calls it the map.

The map is one Markdown file. Links put it where Claude Code, Codex, OpenCode, Gemini CLI and backpass each look for it. Change it once, and all five see the change in their next session.

The map holds house rules, a "who does what" list, and a routing table. The routing table says: for this kind of task, go to this folder and read these files first.

5. Layers and rooms

Context comes in layers, from broad to narrow: the map, each tool's own settings, a repo's rules, a room, and the work in hand. An agent loads only what its task needs.

A room is a folder for one kind of work, such as writing or software. Its CONTEXT.md names the input, the task, the output and a check.

Nothing outside writes into the map or the rooms. A tool may propose an edit. The owner applies it.

Shell tests check the structure, with no model calls: 58 pass, 0 fail (2026-10-30). A probe would ask each agent for a word from the map, to prove it loaded. It costs tokens and was not run. designed, not proven

6. What the owner added

The owner runs a private fork of Firstmate with two additions:

  • Scouts run a plain-English checker on their report before they say "done". It flags long sentences and vague words.
  • Notes from the agent's own memory reach the curated facts file only after review.

The first one has a cost. It makes Firstmate depend on the owner's context system, so one test now fails. The owner keeps that trade-off. Read the case.
