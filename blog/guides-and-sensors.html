Guides, sensors, and the rules I'm still begging for

Mapping my agent setup onto the harness engineering frame, honestly, and picking the next three sensors

1. What "harness" means here

A car has an engine, the car the factory built around it, and the things you add for your own roads: a roof rack, a dashcam, a parking sensor.

Coding agents have the same three layers. The model is the engine. A coding agent like Claude Code or Codex is the first harness, built by the people who make the agent. Around that sits the "outer" harness: everything I put in place for my own projects. Birgitta Boeckeler and Chris Ford call that outer layer "what we can control". Their talk is about harnessing "not the model but ... the agent".

model  <  coding agent's harness (Claude Code, Codex)  <  my outer harness
          built by the agent's makers                     rules, skills, scripts, hooks, gates

The talk draws this as three rings: "We can expand the coding agent harness." See the slide in Harness engineering beyond skills (Birgitta Boeckeler and Chris Ford, Thoughtworks).

The goal they name is trust: "We want to increase our trust in ... the coding agent output", so that changes ship "safely, quickly, and in a sustainable way", and my review time goes where it's needed.

2. Guides and sensors

Before the agent acts, or after?

A recipe tells you what to do before you cook. Tasting the soup tells you what actually happened.

  • Guides are feedforward: things given to the agent "in anticipation of what it might have to know and what it might do wrong". Rules files, skills, reference docs, how-tos.
  • Sensors are feedback: checks that run after the agent acts, "so that it can self-correct before we even look at it". Static analysis, logs, tests, a browser, a review agent.

The talk's slide shows guides feeding forward, sensors feeding back, and a human steering both. See Harness engineering beyond skills (Thoughtworks).

A human sits above both. When the same thing keeps going wrong, the question is: "is there a sensor I can add? Is there something I should add to the guides?"

3. CPU and GPU

Who does the checking?

A ruler and a second opinion both check a shelf. Only one gives the same answer every time.

The talk splits both guides and sensors by what runs them:

  • CPU computational: deterministic scripts. A linter, a type checker, a test, a log. "An observation of what's really going on." Cheap and repeatable.
  • GPU inferential: a model's judgement. A review agent is "an LLM judging what another LLM did ... still probabilistic". Good for fuzzy questions.

Chris Ford's advice: successful teams "try to offload from the GPU to the CPU". Once a rule is objective, turn it into a script. It's more reliable, and "a lot more token efficient".

4. Prompt, skill, folder, script: four ways to steer an agent

How much does the model decide?

You can teach someone to cook by talking them through it, by handing them a recipe card when they need it, by giving them a labelled kitchen, or by giving them a machine that only does it one way.

Harnesses sit on the same line. On the left, the model decides almost everything. On the right, scripts decide and the model fills in the gaps.

FirstMate sits on the right. It's script-driven: hooks, guarded merge scripts and refusals that don't depend on the model remembering a rule. My context folders sit one step left. They're folder-controlled: numbered stage folders, a contract file per stage, and a few scripts.

The far end is different in kind. Most of a harness pushes things at the agent. A user-invoked skill is pulled by a person, on purpose. Two of these matter most for people new to AI:

  • grill-me (from Matt Pocock's skills; I use a variant, grill-with-docs): before any work, the agent interviews you until the ask is settled. New users often don't know what to ask for. This fixes that.
  • "Introduce me to AI": an onboarding mode that explains each step as it goes. This is an idea, not a built skill yet.

My guess: used well, these two get people started faster than any amount of rules. They teach the person, not the agent.

5. The harness arena

This section also has its own page: the harness arena.

How do other setups compare, and what's become standard?

A spec sheet doesn't tell you how a car drives. It does tell you what's missing.

I think of this as an arena, not a ranking. New harnesses enter it. Techniques that several harnesses share get compared side by side. And some techniques stop being special: rules files like AGENTS.md, worktrees and skills are close to standard now, so I mark them that way. The arena holds two views: the tier list below, and my own radar in "How we composed ours".

How often it runs: it isn't scheduled yet. The tier list ran once, on 27 October. The radar was drawn on 17 October and refreshed for this post.

Folder as harness

A good kitchen is half the recipe. If the knives are where the knives go, you don't need a note saying where the knives go.

In a folder-controlled harness, the agent is steered mostly by where things are. There are still prompts, but they live inside files: a CONTEXT.md per stage, a numbered folder per step, a script next to the step that checks it. The folder is basically a GitHub repo.

ICM (Jake Van Clief's Interpretable Context Methodology) works this way. Numbered stage folders carry the order; each stage has a one-page contract of inputs, process and outputs; one agent reads the right files at the right time. My context folders follow it.

Vercel's d0 is the other example. It's Vercel's internal agent that turns data questions into SQL. In "We removed 80% of our agent's tools" (Andrew Qu, 22 Dec 2025), the team says they replaced 17 specialised tools and heavy prompt engineering, and "stripped the agent down to a single tool: execute arbitrary bash commands". The agent (Claude Opus 4.5, per the post) reads their "Cube semantic layer as a directory of YAML, Markdown, and JSON files" with grep, cat, find and ls. On their five test queries, success went from 80% to 100%, runs got about 3.5 times faster, and token use fell 37%. They add that it "only worked because our semantic layer was already good documentation."

What I haven't verified: the d0 numbers are Vercel's own, on five queries, and I haven't tried it. I haven't scored d0 on the twelve parts.

Why is a folder more deterministic than a prompt?

  • Versioned. Every change to a file is a Git commit. You can see when a rule changed and undo it.
  • Diffable. You can compare two versions line by line. A rule you typed into a chat is gone the moment the chat ends.
  • Reviewed. A change to the folder can go through review like code. No one reviews a prompt typed at 2 a.m.
  • Same steps every time. A script in the folder runs the same way on every call. The model still reads the files, but what it reads is fixed.

It's still not fully deterministic: the model chooses which files to read and what to do with them. That's why it sits between skills and scripts.

7. Where my checks sit on the path to production

When does each check fire?

A typo caught while you write costs a keystroke. The same typo caught after printing costs a reprint.

The talk places guides and sensors along the path a change travels: the coding session, integration, the CI pipeline, then things that run repeatedly (drift detection) and in production (runtime feedback). Early checks are "cheap and quick to run, cheap to fix". Late ones are expensive to run, expensive to fix, and need processes around them.

The talk's slide: "Strategic placement of guides and sensors across the path to production." See Harness engineering beyond skills (Thoughtworks).

Here are my real checks on that path.

Two things stand out. Most of my checks sit in the coding session and at integration, which is the cheap end. That's good. But the starred ones in the session column are the "half sensors" from section 9: cheap to run, yet only when an agent remembers.

The other end is thin. The scheduled column watches my rules and my setup, not the work itself. And in production there's nothing: no check that a published page still renders, or that a link I shipped still opens.

Test: firstmate's .github/workflows/ci.yml runs bin/fm-test-run.sh --check-coverage; the dotfiles context-tests.yml runs on pushes that touch context/; harness-check (weekdays), backpass (nightly) and the routine scan (daily) are launchd agents in home.nix; the weekly corrections review I run by hand.

8. Where I'm still begging

The talk has a good phrase for most rules files: "a lot of begging. You should always do this and you should never do that."

Mine has plenty. Each of these is a rule with no sensor behind it:

  • "Secrets never go in files, commits, logs or prompts." No scanner checks.
  • "Verify, then report." Nothing checks that a command ran before the report says it did.
  • "Check light, dark and phone width before handing over" (blog room, step 5). An agent has to remember.
  • "Before you give a link, open it." My last post found this broken five times in a week.

This is the "battle of the markdown files". When a rule keeps breaking, more wording rarely helps. A check might.

9. Half a sensor

The lesson from the orange rows

A smoke alarm that only works when you press the test button isn't a smoke alarm.

The orange rows in the table taught me the most. plain-check is a real CPU sensor: no model, no network, the same answer every time. But it only runs when an agent decides to run it. So the decision is still GPU. The script is deterministic; whether it fires is not.

Compare the cd check. It's a hook. The agent can't forget it, because the agent never calls it. That's the difference between a sensor and a tool that happens to check things.

hook-wired script   -> fires every time          (full sensor)
script in a skill   -> fires when the model asks (half a sensor)
rule in markdown    -> no check at all           (begging)

10. Three sensors to add next

Each one moves a rule I'm currently begging for onto the CPU, and wires it so it can't be skipped.

  1. A secret and privacy scan at commit time. A pre-commit hook: a secret scanner like gitleaks (the talk's own example) plus my own pattern list for home paths, emails and private names. Today the privacy scan is a grep the agent writes and counts itself.
  2. plain-check on every draft, automatically. Run it when a file under drafts/ is written or committed, and hand back only the failures. The talk goes further with a "sensors sidecar": a small process that re-runs tests, lint, type checks and more every 10 to 60 seconds and keeps a status table the agent can read. It calls this kind of output an "agent optimized view", and custom lint messages "positive prompt injection".
  3. A link check before a report goes out. A script that opens every URL in a final message and fails on any that don't load, or that only load on this machine. This is the rule that already broke five times.

My guess: the third is the hardest, because "the final message" isn't a file. It may need a turn-end hook rather than a commit hook.

Update, 2 November: all three are now in place: a secret scan at commit, a plain-language check on drafts, and a link check before replies.

11. The goal is continuous delivery

The end goal isn't a clever harness. It's the old one:

"Continuous Delivery is the ability to get changes of all types ... into production, or into the hands of users, safely and quickly in a sustainable way."

Guides make the first attempt better. Sensors catch what the guides missed, before I do. The human loop turns repeated mistakes into new guides and sensors. Moving checks from GPU to CPU makes each step cheaper and more reliable, and that's where the speed comes from.

12. What's still rough

  • The table is my reading of my own setup. Some rows could fairly go in two columns. The same goes for the harness types in section 5.
  • The tier scores are from 27 October, read from docs and papers, not tested. All twelve parts count the same.
  • I haven't measured anything. The talk ran the same task with a small model, no guides, from a clean "bill of health", once with sensors and once without. With sensors everything stayed green; without, lint and structure went red and coverage slipped. I haven't run anything like that.
  • Green isn't proof either. The talk shows a file with 100% statement coverage, no unit tests of its own, and 13 survivors under mutation testing. My CI checks coverage; nothing checks test quality.
  • No-mistakes mixes CPU and GPU steps in one gate. I don't yet know which of its catches came from which.
  • The talk's open question applies here too: "how many guides can you actually just delete" once a sensor covers them? I don't know yet.

The talk shows the end state of that experiment as two dashboards, one with sensors and one without. See Harness engineering beyond skills (Thoughtworks).
