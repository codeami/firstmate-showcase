Your corrections are your next rules

How I turn a week of "no, not like that" into rules my agents read, without letting them edit their own rules

Ashish Raina2 Nov 20266 min read

1. The question

A good coach watches the game tape. Not to relive the match, but to spot the mistake that keeps coming back, and drill it once.

My game tape is my chat history. Every time I correct an agent, I'm writing a rule out loud and then throwing it away. So one Sunday I asked an agent to go back through the week and pick them up:

Look back at our chats from this week. List every time I corrected you or redid your work. For each one, tell me whether the fix belongs in project instructions or a skill, or nowhere because it was a one-time thing. Then write the exact wording I should add.

It came back with a review page I could read on my phone: every correction in my own words, where the fix belongs, and the exact wording to add. This post walks through how that page was made, and what I did with it.

2. How the review ran

What did the agent actually read?

Think of sorting a week of mail: first throw out the flyers, then read what's left.

  1. Find the chats. It listed every session log changed in the last seven days: 190 files across 30 project folders.
  2. Keep only what I typed. In my setup, agents talk to agents a lot. It dropped tool output, system reminders, hook messages, orchestrator pings and wake-ups, and the briefs one agent writes for another. 875 turns became 502.
  3. Read each one with the reply before it. A correction only makes sense next to what it corrected.
  4. Group repeats. Five different "this link doesn't work" messages are one problem, not five.
  5. Check the existing rules. Before proposing anything, it read the rule files I already have, so it could say "already covered" instead of writing a duplicate.

It also wrote down what it did not count: retries after network errors, my own typos, and plain "yes" approvals. That list matters as much as the main one; it's how I can tell the agent didn't pad the numbers.

Test: the report lists every correction with its date and my exact words, so each count can be checked by hand.

3. Three places a fix can go

Where does a lesson belong?

Some lessons go on the fridge, some go in the recipe book, and some you just remember for tonight.

PlaceWhen it loadsGood for
Project instructions (AGENTS.md and its kin)every sessionthings that should be true every time, like "check a link opens before you send it". They cost tokens in every session, so they must earn their place.
A skillonly when a task matches it"how to do X" steps that only matter when doing X
Nowherenevera one-time fix. "The day color is not sticky" was a bug on one page. As a rule it would only add noise.

In practice there was a fourth answer: already covered. A rule existed and the agent broke it anyway. That one teaches the most, and I come back to it in section 5.

4. The results in numbers

46 corrections in one week, in 12 groups.

New wording proposed (P1 to P4)18I approve or edit them
Already covered by a rule14nothing to add; the rule was missed
One-time fixes11nothing
Needs tooling, not wording3a separate task

No fix landed in a skill this week. The closest was "skills and hooks did not fire", and a rule can't fix a skill that doesn't load, so that became a task instead. I like that the agent said so rather than forcing something into the skill column.

Test: 18 + 14 + 11 + 3 = 46, and each row of the review page carries its count.

5. Three real examples

Links that did not open (5 times)

"report is not linking" · "Cant see on mobile"

The agent gave links without opening them first, and many were local-only addresses that never open on a phone. Proposed (P1), for the shared instructions every agent reads:

Before you give a link, open it and check that it loads. He often reads on his phone: give the Tailscale […] address when there is one, and say "opens only on this Mac" when there is not.

Making what already existed (7 times)

"wishperX is a duplicate tool ?" · "We are sending scouts to learn about scouts"

It installed a tool when one already did the job, and sent research agents to find things it could have just looked up. An old rule covered research agents only; the same mistake also showed up as a web search, an install, a new file and a new script. Proposed (P2):

Look before you make. Before a web search, a scout, a new install or a new file, look for what already exists […]. Extend what is there; do not start a second copy.

Already covered, still broken (3 times)

"eli5 this to me"

I already have "talk very simply" in two rule files. The review said so, proposed no new wording, and added a caveat I agree with: when a rule exists and still breaks, more wording probably won't help. A check might. It labelled that last part "a guess", which is the right label.

6. I approve; the agent never edits its own rules

Who gets to change the rules?

The agent that makes the mistakes doesn't get to rewrite its own rules. The review is read-only. Its output is a page and four proposals, presented as one decision. Nothing changes until I say so, and then a separate step applies the change.

Two reasons for the gate. A model's guess shouldn't get the authority of something I said. And a review that can only propose stays honest about what it's unsure of: this one flagged that P4 might overlap a rule file it hadn't read.

This is the same idea as Kun Chen's backpass, which reads logs from many tools overnight and proposes rule edits with quoted evidence. Here I ran it by hand, as one prompt, to see what a week looks like.

7. Try it yourself

Paste this into a coding agent that can read its own session logs. Claude Code, for example, keeps them in the projects folder of its own settings folder.

Look back at our chats from this week. List every time I corrected you or redid your work. For each one, tell me whether the fix belongs in project instructions or a skill, or nowhere because it was a one-time thing. Then write the exact wording I should add.

Read only my own messages, not tool output or messages between agents. Check each fix against the rules I already have. Do not edit any rule file; propose only.

The first paragraph is my original prompt. The second adds the three things that made the result trustworthy: only my words, checked against what exists, and no edits.

8. What's still rough

  • One week is a small sample. Some groups have three items.
  • The agent judges its own mistakes. It may miss a correction I phrased politely.
  • Two groups broke rules that already exist. Wording is not enforcement.
  • P1 to P4 were waiting for my decision when I wrote this. I approved all four on 2 November.
