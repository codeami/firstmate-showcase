Harness flow

How one task is checked

Follow one task from the owner's ask to the notebook. Nothing lands until it has been checked three times.

See it as a picture. The Harness flow map shows each step. A heavy outline means the owner decides. A green fill means the supervisor reads real state. It does not take a worker's word. Click any step.

One task, six parts

  1. Ask. The owner asks in plain words. The supervisor sorts the ask.
  2. Instruct. The supervisor writes a brief. Then it starts one worker in its own copy of the code.
  3. Run. The worker works. Short status lines say where it is.
  4. Check. The supervisor reads real state: git, the forge and the files.
  5. Decide and land. The owner decides. Only then does the work land.
  6. Remember. Keep what was learned, after review.

Three checks

  1. The worker checks its own work. It checks each claim with a command or a file read. It reports with evidence. It may not close a task while a question for the owner is open.
  2. The gates check it again. Hooks block unsafe actions. Shell tests check the rules. Before code is pushed, a gate runs review, tests, docs and lint. the full gate was not run for this site
  3. The owner gives the word. Only the owner can merge, publish, send or spend.

Hooks turn rules into checks

A rule in a text file is advice. A hook is a script the tool must run. Hooks turn the most important rules into checks.

The owner's Claude Code hooks, checked on 2026-10-30:

  • Before a shell command: block file writes through the shell, and say "use the editor tools". This works. It blocked commands in the scout's own session.
  • Before a shell command: block commands that would print a secret. installed, not proven
  • When the owner sends a prompt: warn on text shaped like a key. It never blocks. installed, not proven
  • When the owner says "end of session": remind the agent to write a session note.
  • At session start: rebuild a one-page index of all work folders.

Each hook allows the action if its script is missing. That is safe, but it can hide a broken hook. A read-only health checker now lists hooks, jobs and plugins, so such a gap shows up.

Upstream Firstmate adds its own guards for the supervisor. Some rules stay as text, because a script cannot judge them. "Drafts, not sends" is one. The owner catches those in review.

The owner reviews pages, not a terminal

Every report, plan or draft for the owner becomes an HTML page. A page can hold a diagram, a table and evidence on one screen.

agent writes page.html
  → review tool opens it for the owner
  → owner marks text, writes notes
  → notes go back to the agent
  → agent edits the page, asks again
  → owner approves, or ends the review

The review tool is Lavish, by Kun Chen. It works, and this site was reviewed there.

designed, not proven A weekday morning job that rebuilds the owner's cockpit page. The page itself works by hand. Bearings, an upstream view of what waits on the owner, was not run for this site.

Checks that proved the setup wrong

A claim is worth only the check behind it. Two checks found the setup wrong. Both stay on the site on purpose.

A plain-English rule broke a test

Scouts must now run a plain-English checker before they say "done". That checker lives in the owner's context system. A test says the supervisor must never point back at that system. So the test now fails: 36 pass, 1 fail. The owner keeps the failing test. It reports a real trade-off.

"Scouts run with permission checks on" was false

An earlier manual said so. A check counted the flags on the running workers. All 10 skipped permission checks. Skipping is the standing default. The manual now says so. designed A safer, model-reviewed mode is a one-line switch. It is not switched on.

The pattern

  • Write the claim down.
  • Name the check that would prove it.
  • Run the check, and keep the result even when it is bad.
  • Until a check passes, call the claim "in trial", never a feature.
