Core logic

The core logic, in one page

Most of the logic is not code. It is one rules file that every agent reads, plus the owner's own preferences on top. This page shows the flow, the roles, and the twelve parts of the harness. Open any part to read the live rule text behind it.

1. The pipeline, simply

The owner asks in plain words. The supervisor checks the facts itself first. If it needs more, two scouts look in parallel: one at the market, one at the tech. The owner decides. Then ship workers build, the checks run, and the owner gives the word. Only then does the work land. What was learned is kept.

2. Roles and permissions

Each role is a permission, not a model. Any agent tool can fill any role. The list stays open: a new role is a new line in the rules.

Owner (captain)

Decides. Approves every merge.

Supervisor (first mate)

Orchestrates. Never writes to a project itself.

Scouts

Find facts and report. Nothing is pushed.

Ship workers

One task each, in an isolated copy of the code.

Second mates

Each owns one domain, with its own queue.

The hard rules

  • Only the owner merges, publishes, sends or spends.
  • The supervisor delegates project work. It does not do it.
  • One worker, one task, one disposable copy.
  • A worker may not close a task while a question for the owner is open.
  • Ask before anything destructive or hard to undo.
  • Secrets never go in files, commits, logs or prompts.

3. The twelve parts of the harness

A harness is everything around the model: what it reads, what it may do, and who checks it. Open a part to see how this setup does it, how other systems compare, the honest gaps, and the matching rule text.

Has · Different (does the job another way) · Lacks

The comparison comes from two scout reports dated 2026-10-27. They read public docs, repos and papers. They did not test the tools. "Guess" marks a cell the scouts could not confirm.

Always-loaded context

Here: every tool reads one short map first, about 1.5k tokens. The supervisor also reads its rules file each session.

  • has ICM: three thin layers, about 1.3k to 1.6k tokens; a stage gets 2k to 8k.
  • has Claude Code: CLAUDE.md each session; its docs advise under 200 lines.
  • has OpenCode, Pi: an instruction file plus skill descriptions. Size not stated.
  • lacks Harness-squared, Meta-Harness: they edit or search the harness instead.

Gap: the supervisor's rules file is about 11k tokens, loaded before any work.

Rules

Here: one rules file, plus a written brief for each task. A routing table says which folder to read for which job.

  • has Claude Code, OpenCode, Pi: an instruction file; Claude Code adds path-scoped rules.
  • has ICM: a one-page contract per stage: inputs, process, outputs.
  • different Omnigent: agents and policies in YAML, stacked server, agent, session.
  • different Harness-squared: the system prompt is one of eight parts an editor changes.
Skills

Here: each skill's name and description load every turn. The body loads only when the trigger fits.

  • has Claude Code: each description capped at 1,536 characters; body on use.
  • has OpenCode, Pi, Warp: skill folders, loaded on demand.
  • different ICM: no skill loader; the folder layout does the job.
  • lacks Meta-Harness: none built in.
Memory and decay

Here: at the end of a session, a "stow" step files lessons with decay tiers. Agent memory reaches the curated facts only after review.

  • has Claude Code: auto memory per repo. No decay rule stated.
  • has Harness-squared: lessons kept per domain. No decay stated.
  • different Pi, OpenCode: sessions with compaction; no memory across sessions.
  • different ICM: state is files on disk; no memory layer.
Hooks

Here: scripts the tool must run. They block file writes through the shell, warn on text shaped like a key, and remind the agent to write a session note.

  • has Claude Code: hooks at lifecycle events.
  • has OpenCode: plugin events before and after each tool.
  • different Pi: extensions register event handlers. Omnigent: policies check every action.
  • lacks Warp: none found in its docs. ICM: none.
Isolation

Here: each worker gets its own disposable git worktree. Each second mate gets its own home folder.

  • has Omnigent: nine sandbox providers, plus OS sandboxes.
  • has Claude Code: worktrees, and a shell sandbox that is off by default.
  • different Warp: cloud agents are sandboxed; local agents are not.
  • lacks Pi: "containerise it yourself". Harness-squared: network open, sandbox off.

Gap: a worktree isolates files only. It does not fence the network or credentials.

Orchestrator

Here: the owner talks to one supervisor. Workers are full agent sessions in visible windows. A watcher that uses no tokens wakes the supervisor when needed.

  • has Omnigent: mixes Claude Code, Codex, OpenCode, Pi and others.
  • has Warp: an orchestration host with other agents as children.
  • different Claude Code: subagents and agent teams, all Claude sessions. ICM: folder order is the orchestrator.
  • lacks Pi: skips sub-agents by design.
Review gate

Here: a local gate runs review, tests, docs and lint before the branch leaves the machine. Shell tests check the rule files.

  • different Omnigent: a policy can require approval to push. No test gate.
  • different ICM: every step ends at a check. No push gate.
  • lacks Claude Code: no pre-push gate; PR review comes after the PR exists.
  • lacks OpenCode, Pi: none built in.
Human approval points

Here: only the owner merges, publishes, sends or spends. A decision is a task held for the owner. Reviews happen on HTML pages.

  • has Claude Code: permission modes, and hooks that block whatever the model says.
  • has OpenCode: allow, ask or deny, per agent. Omnigent: ask before shell writes; a hard spend cap.
  • has ICM: the owner reviews at every stage boundary.
  • lacks Pi: no permission prompts. Harness-squared: none documented.

Gap: the approval and spend rules are prose. The model may not follow them. Omnigent writes the same ideas as enforced policy.

Self-improvement

Here: a tool called backpass reads past transcripts and proposes rule edits. The owner applies each one by hand.

  • has Harness-squared: propose, test and combine edits within each task. No human step.
  • has Meta-Harness: searches harness code using full run traces.
  • lacks Claude Code: auto memory only. OpenCode, Pi: none built in.
  • lacks Omnigent: on its roadmap, not shipped.

Gap: a proposed edit is argued from past evidence. It is never tested by replaying a task.

Sync across machines

Here: links put the one map where five tools look for it. The supervisor's rules reach running sessions through git.

  • has Omnigent: live sessions shared by URL; phone, web and desktop.
  • has Warp: skills, rules and memory shared across a team (vendor claim).
  • different Pi: packages through npm or git. OpenCode: reads Claude Code's file as a fallback.
  • lacks Harness-squared, Meta-Harness: none.

Gap: agent memory does not sync between machines. (Guess: not checked.)

Vision and goals

Here: a private owner's layer holds current priorities and preferences, on top of the shared base.

  • different Meta-Harness: one written objective per domain.
  • lacks ICM: its paper defines no goals layer.
  • lacks Claude Code, OpenCode, Pi, Warp, Omnigent, Harness-squared: none.

The owner's layer

Personal rules on top of the base; private. Only the section names are shown:

  • Provider routing
  • Working style
  • Domains
  • Hardware

4. Live rule text
